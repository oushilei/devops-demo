# Docker Registry 数据卷实验（2026-10-12）

> Week 2 Day4 前置实验
> 目标：验证「容器删除后数据是否会丢」的真实条件

## 一、实验背景

启动本地镜像仓库时遇到容器名冲突：

    docker run -d -p 5000:5000 --name registry registry:2
    docker: Error response from daemon: Conflict. The container name "/registry" is already in use.

## 二、排查过程

### 步骤 1：查看旧容器状态

    $ docker ps -a --filter name=registry
    CONTAINER ID   IMAGE        CREATED       STATUS                     PORTS
    51b01bfaccde   registry:2   8 days ago    Exited (255) 4 days ago    0.0.0.0:5000->5000/tcp

判读：
- 镜像正确（registry:2）
- Exited (255)：Docker daemon 重启时强制停容器给出的通用退出码
- 端口映射仍在，配置完好

### 步骤 2：inspect 精确提取元数据

    $ docker inspect registry --format '{{.State.Status}} | {{.Config.Image}} | {{.HostConfig.PortBindings}} | {{.Created}}'
    exited | registry:2 | map[5000/tcp:[{ 5000}]] | 2026-10-03T14:18:37Z

结论：配置完整，可原地复活。

    $ docker start registry
    $ docker ps | grep registry
    51b01bfaccde   registry:2   Up 7 seconds   0.0.0.0:5000->5000/tcp

### 步骤 3：检查仓库里有没有数据（决定性的一步）

    $ curl http://192.168.2.150:5000/v2/_catalog
    {"repositories":["devops-demo"]}

关键发现：仓库里有数据。而这个容器创建时没有 -v 参数，
数据存在「容器可写层」，容器一删就丢。

## 三、数据丢失风险的实证（对照实验）

| 时间点 | 操作 | _catalog 返回 |
|---|---|---|
| 删除前 | 旧容器（未挂卷） | {"repositories":["devops-demo"]} |
| 执行 docker rm -f | 容器销毁 | — |
| 重建后 | 新容器（挂了命名卷） | {"repositories":[]} |

实测：

    $ docker rm -f registry
    registry

    $ docker run -d -p 5000:5000 --restart unless-stopped \
        -v registry-data:/var/lib/registry \
        --name registry registry:2
    223659dc38bc03e9247b2d213c8dc473c6d240e6c2fb3405e4bab2f33be53

    $ docker volume ls | grep registry
    local     registry-data

    $ curl http://192.168.2.150:5000/v2/_catalog
    {"repositories":[]}

{"repositories":[]} 不是失败，是新卷为空的正确表现。

## 四、结论

### 1. 容器删除是否丢数据，取决于数据在哪

| 数据位置 | 创建方式 | 容器删除后 |
|---|---|---|
| 容器可写层 | docker run 未加 -v | 数据丢失 |
| 命名卷 | -v 卷名:/容器内路径 | 数据保留在宿主机 |
| 绑定挂载 | -v /宿主机路径:/容器内路径 | 数据保留在宿主机指定路径 |

### 2. Exited (255) 的成因

宿主机 Docker daemon 重启时，所有运行中的容器被强制停止，退出码 255。
这不是容器坏了，是被重启带走的。用 docker start 可按原配置复活——
容器的配置（镜像、端口、卷、网络、环境变量）存在元数据里，永久保留；
只有运行时状态（进程、内存）会丢失。

### 3. 生产环境的教训

| 教训 | 做法 |
|---|---|
| 有状态容器必须挂卷 | -v 或 --mount |
| 有状态容器必须自动重启 | --restart unless-stopped |
| 删除容器前先确认数据位置 | docker inspect 看 .Mounts 字段 |
| docker start 优于 rm -f + run | 前者复用原配置 |

## 五、面试话术

Q：容器删除后数据会丢吗？
A：取决于数据存在哪里。没挂卷时数据在容器可写层，docker rm 时随容器销毁；
   挂了卷（命名卷或绑定挂载）数据实际在宿主机上，容器删除不影响。

Q：宿主机 Docker 重启，容器会怎样？
A：所有运行中的容器被强制停止，退出码 255。但容器的配置保存在元数据里不会丢，
   用 docker start 可按原配置恢复。生产环境要加 --restart unless-stopped 实现自动恢复。

Q：怎么判断一个容器的数据在不在卷里？
A：docker inspect <容器名> 看 .Mounts 字段。为空说明数据在可写层，有风险。

Q：修改 /etc/docker/daemon.json 要注意什么？
A：必须先读原文件再合并，不能直接覆盖。覆盖会丢失 exec-opts、registry-mirrors
   等关键配置。特别是 K8s 环境，exec-opts: ["native.cgroupdriver=systemd"] 丢失
   会导致 kubelet 与容器运行时 cgroup driver 不一致，集群异常。

## 六、本次踩的坑与修正

| 环节 | 风险动作 | 正确做法 |
|---|---|---|
| 容器名冲突 | 直接 docker rm -f registry | 先 ps -a + inspect 查清是什么、有没有数据 |
| 重建仓库 | 直接覆盖（会丢已推镜像） | 先 curl /v2/_catalog 确认数据量 |
| 改 daemon.json | 直接 > 覆盖写入 | 先 cat 读原文件，合并后再写 |
