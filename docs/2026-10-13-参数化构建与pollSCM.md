# 参数化构建 + poll SCM 自动触发（2026-10-13）

## 目标
让流水线从「手动点、参数写死」变成「可选参数 + 代码一推就自动跑」。

## 一、参数化构建

### 新增的两块

    parameters {
        choice(name: 'BRANCH', choices: ['main', 'dev'], description: '要构建的分支')
        string(name: 'TAG', defaultValue: 'v1', description: '镜像标签')
    }

    triggers {
        pollSCM('H/5 * * * *')
    }

### 验证结果

    $ curl -s http://192.168.2.150:5000/v2/devops-demo/tags/list
    改脚本前： {"name":"devops-demo","tags":["v1"]}
    参数化后： {"name":"devops-demo","tags":["v1","v2"]}

同一个脚本产出了两个版本，参数化生效。

## 二、踩坑：parameters 的参数在 sh 里取不到值

### 现象

    + docker build -t $IMAGE_NAME:$TAG .
    Invalid argument "devops-demo:" for "-t, --tag" flag: invalid reference format

`$IMAGE_NAME` 有值，`$TAG` 为空。

### 根因

| 变量 | 来自 | shell 里 |
|---|---|---|
| $IMAGE_NAME | environment 块 | 有值（Jenkins 无条件注入） |
| $TAG | parameters 块 | 空 |

- `${params.BRANCH}`（Groovy 层）能取到值 —— Jenkins 会用默认值填充 params 对象
- `$TAG`（shell 环境变量）取不到 —— **首次运行时 job 尚未注册为参数化任务，
  环境变量未注入**

### 三条取值通道

| 通道 | 写法 | 可靠性 |
|---|---|---|
| Groovy 直读 params | `${params.TAG}`（双引号） | 总有值（默认值兜底） |
| shell 环境变量 | `$TAG`（单引号） | 参数注册前为空 |
| environment 中转 | `IMAGE_TAG = "${params.TAG ?: 'v1'}"` + `$IMAGE_TAG` | 最可靠 |

### 修复：在 environment 里显式映射 + Elvis 兜底

    environment {
        BRANCH_NAME = "${params.BRANCH ?: 'main'}"
        IMAGE_TAG   = "${params.TAG ?: 'v1'}"
    }

统一规则：**shell 里出现的一切变量，必须先在 environment 里定义过。**&#8203;

## 三、poll SCM 自动触发

### 配置

    triggers {
        pollSCM('H/5 * * * *')
    }

### 结果

构建 #7（16:14）成功，**由 SCM 变更启动** —— 未手动点任何按钮。

## 四、关键发现

### 1. 轮询的基准是「上次成功构建的 revision」

    15:57  push 代码
    16:04  轮询检测到变化 → 触发 #6 → 失败（dev 分支不存在）
    16:14  轮询再次检测到变化 → 触发 #7 → 成功

#6 失败后基准未推进，所以 #7 又被触发。
**失败会自动重试，这是有意设计。**&#8203;

### 2. 自动触发的构建使用参数的默认值

    #6 手动触发 → BRANCH=dev（手选） → 失败
    #7 自动触发 → BRANCH=main（默认） → 成功

自动触发时没有人在场，没人能选参数 → 只能用默认值。
**推论：parameters 里第一个选项必须是「一定能跑通」的值。**&#8203;

### 3. 轮询成功 ≠ 构建能拉下来

| 动作 | git 命令 | 数据量 | 结果 |
|---|---|---|---|
| 轮询 | git ls-remote | 几百字节 | 0.97 秒完成 |
| 构建拉代码 | git fetch | 几 MB | 曾失败（TLS 中断） |

**小数据量查询能通 ≠ 大数据量传输能通。**&#8203;

## 五、网络问题排查

    fatal: unable to access 'https://github.com/oushilei/devops-demo.git/':
    GnuTLS recv error (-110): The TLS connection was non-properly terminated.

- 性质：**网络层问题**（TLS 连接被中断），非 Jenkins 配置问题
- 判断依据：**同一个配置上次能拉、这次不能拉 → 网络问题**
- 解法：开启代理后 fetch 成功

## 六、cron 表达式 H/5 * * * *

字段顺序：分 时 日 月 周

    H/5  → 每 5 分钟（起始分钟由 hash 决定）
    *    → 每小时 / 每天 / 每月 / 每周

**H = Hash，Jenkins 特有语法。**&#8203; 它根据 job 名算出一个稳定偏移量，
让多个 job 的触发时间自动错开，避免同一时刻集中请求造成尖峰。
（若 100 个 job 都写 */5，会在 0/5/10 分同时请求，容易被 GitHub 限流。）

## 七、面试话术

Q：Jenkins 怎么实现代码提交后自动构建？
A：两种机制。
   Webhook：GitHub 收到 push 时主动 POST 通知 Jenkins 的 /github-webhook/ 端点，
            实时（秒级），但要求 Jenkins 公网可达。
   Poll SCM：Jenkins 按 cron 定时轮询 Git 仓库，对比「上次成功构建的 revision」
             与「远程最新 revision」，不同则触发，有延迟但不需要公网。
   内网环境用 Poll SCM。代价是延迟、无效请求消耗、GitHub API 限流。

Q：cron 里的 H 是什么？
A：Jenkins 特有的 Hash 符号，不是标准 cron 语法。根据 job 名计算稳定偏移量，
   让多个 job 触发时间错开，避免尖峰。H/5 = 每 5 分钟一次，起始分钟由 hash 决定。

Q：Pipeline 参数在 sh 里取不到值怎么办？
A：parameters 的参数会填充进 params 对象，但不保证注入 shell 环境变量
   —— 首次运行时 job 尚未注册为参数化任务。可靠做法是在 environment 里显式映射
   并用 Elvis 兜底：IMAGE_TAG = "${params.TAG ?: 'v1'}"。

Q：Jenkins 拉代码报 GnuTLS recv error (-110) 怎么排查？
A：这是 TLS 连接被非正常中断，属网络层问题。先在容器内测连通性
   （docker exec jenkins curl -sI https://github.com --max-time 10）；
   时通时不通 = 间歇性抖动，重试即可；持续不通则考虑换 SSH 协议、
   配代理、或用国内代码托管。判断依据：同一配置上次能拉这次不能拉 = 网络问题。
